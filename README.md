# GIS Layers — управление картографическими слоями на vedro

Тестовое задание: интерфейс управления слоями «температура / ветер / инсоляция»
на React 19 + TypeScript с состоянием в [`vedro`](https://www.npmjs.com/package/vedro).

Для каждого слоя: включение/выключение, прозрачность, статус `loading / success / error`,
повторная загрузка после ошибки, имитация запроса к API при включении.
Сверх ТЗ — карта MapLibre, страница стресс-теста и журнал запросов; зачем каждое — ниже.

---

## 1. Запуск

Нужен Node **20.19+ / 22.12+** (требование Vite 8) и Yarn через corepack:

```bash
corepack enable        # один раз на машину, даёт команду yarn нужной версии
yarn install
yarn dev               # http://localhost:5173
```

| Команда          | Что делает                                         |
| ---------------- | -------------------------------------------------- |
| `yarn test`      | 6 тестов (Vitest), ~3 с                            |
| `yarn typecheck` | `tsc -b` в строгом режиме                          |
| `yarn lint`      | ESLint, `no-explicit-any: error`, 0 предупреждений |
| `yarn build`     | production-сборка                                  |

`any` запрещён не на словах: husky + lint-staged прогоняют ESLint на каждом коммите.

**Что посмотреть в интерфейсе:**

- `/` — панель слоёв, карта, журнал запросов. Включите **«Хаос-режим»** и сделайте
  у одного слоя «вкл → выкл → вкл»: через ~2.5 с в журнале появится
  `ОТВЕТ ОТБРОШЕН` — так выглядит обработанная гонка.
- `/stress` — 3 / 50 / 100 / 500 слоёв со счётчиком рендеров в каждой строке.
  Переключите любой слой: счётчик вырастет только у него. _(Счётчик на React Profiler —
  работает в `yarn dev`, в production-сборке React его не вызывает.)_

## 2. Архитектура

```
 API        LayersApi (интерфейс) ← createMockLayersApi
              │ fetchLayer(id, signal)
 Логика     createLayersController — загрузка, отмена, гонки.
              │ Обычный TS, не знает про React. Единственное место записи в стор.
 Состояние  Vedro<{ byId, allIds }> — инстанс создан вне React
              │ on("allIds")                 │ on("byId")
 UI         LayerPanel → LayerRow × N      MapView → MapLayerBinding × N
```

```
src/
  domain/   модель: Layer, LayerLoad (дискриминированное объединение)
  api/      интерфейс LayersApi + mock
  core/     контроллер и журнал событий — чистый TS
  state/    стор vedro и хуки подписки
  ui/       панель слоёв
  map/      карта MapLibre — вся папка опциональна
  pages/    / и /stress
```

**Панель и карта подписаны на одни данные и ничего не знают друг о друге.** Карта —
второй независимый потребитель стора: папку `src/map/` можно удалить (плюс две строки
подключения в `MapPage`), и типы, линтер и все тесты остаются зелёными. Это проверено,
а не заявлено — без второго потребителя тезис «UI отделён от состояния» остался бы словами.

Контроллер — фабрика с замыканием, а не класс: методы не используют `this`, поэтому
`const { setEnabled } = useLayersController()` безопасно и ссылки стабильны без `.bind`.

## 3. Особенности vedro, повлиявшие на решения

Документации у пакета немного, поэтому я прочитал исходники `vedro@1.1.0`.
Несколько особенностей определили архитектуру:

- **Асинхронный `dispatch`.** Проверка `isAsyncFunction` в `lib/helpers/typeCheck.js`
  не распознаёт async-функции, поэтому `dispatch(async fn)` не меняет состояние.
  → Вся асинхронность вынесена в контроллер, в стор попадают только готовые значения.
- **`useSelector` подписан на всё состояние (`"@state"`)** и сравнивает результат через
  `JSON.stringify` — на 100+ строках это лишняя работа на каждый диспатч.
  → Свой хук на `useSyncExternalStore` с подпиской по ключу: `on(key)` и `get(key)`
  из ядра vedro подходят к нему напрямую.
- **Верхний уровень состояния копируется при каждом диспатче**, а новые ключи
  добавлять нельзя. → Состояние — ровно два ключа, `{ byId, allIds }`.
- **Пакет в формате CommonJS.** В Vite 8 импорт по умолчанию отдаёт объект модуля,
  а не класс. → Импорт нормализуется в одном месте, `src/state/layersStore.ts`.

Подробности с цитатами исходников могу показать на встрече.

## 4. Гонки

Сценарий: «вкл → выкл → вкл» быстрее, чем отвечает API. Защиты две, и нужны обе:

| Механизм                           | Что защищает                                   | Чего не умеет                                    |
| ---------------------------------- | ---------------------------------------------- | ------------------------------------------------ |
| `AbortController.abort()`          | сеть — рвёт запрос, пока ответ не пришёл       | если ответ уже пришёл в браузер, отменять нечего |
| проверка `inflight.get(id) !== ac` | состояние — опоздавший ответ не пишется в стор | не освобождает соединение                        |

Токен поколения — **сам `AbortController`**: при каждом новом запросе в `inflight`
кладётся новый объект, при выключении — удаляется. Ответ принимается, только если
его контроллер всё ещё текущий. Отдельный счётчик поколений не нужен — сравнивается
тот самый объект, разъехаться с реальностью нечему.

Правило: **в состояние пишет только последний запрос**, порядок определяется моментом
клика, а не прихода ответа.

Правильная обработка гонки выглядит как «ничего не произошло», поэтому её видно
в журнале. Mock в **хаос-режиме** делает нечётный запрос слоя медленным (2.5 с)
и глухим к `abort` — так ведёт себя сервер, который ответ уже отправил. Это
воспроизводит ровно то окно, ради которого существует вторая защита.

## 5. Масштабирование 5 → 100+

**Рендеры — O(1) на действие.** Переключение слоя делает `dispatch("byId", …)`:

- подписчики `allIds` (список) не уведомляются — `LayerPanel` не перерисовывается;
- уведомляются N строк, но React сравнивает снапшот **до** планирования рендера:
  у N−1 строк `getSnapshot` возвращает ту же ссылку на `Layer`, рендер не планируется.
  Новый объект создаётся только для изменившегося слоя.

Проверено тестом: 100 слоёв, переключение одного — **ровно 1 рендер строки**.
Тест проверен мутацией: если пересоздавать все слои, он падает (200 рендеров вместо 101).

**Где предел.** Каждый `patch` копирует `byId` (`{ ...byId, [id]: next }`) — O(N)
по памяти. На 100–1000 слоях это микросекунды. На тысячах, особенно при частых
обновлениях (ползунок, real-time поток), следующий шаг — отдельный `Vedro`-инстанс
на слой: диспатч перестаёт зависеть от N совсем. Для DOM на 500+ строк — виртуализация
списка.

## 6. Типизация

Статус загрузки — дискриминированное объединение, а не набор флагов:

```ts
type LayerLoad =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; payload: LayerPayload }
  | { status: "error"; error: LayerError };
```

Форма `{ loading: boolean; error?: string; data?: T }` позволяет скомпилировать
`{ loading: true, error: "fail", data }` — состояние, которого не бывает.
Здесь такое не компилируется, а `assertNever` в `switch` превращает новый статус
в ошибку компиляции во всех местах, где он не обработан.

Помимо `strict`: `noUncheckedIndexedAccess` (`byId[id]` — это `Layer | undefined`,
и проверку нельзя забыть), `exactOptionalPropertyTypes`, `verbatimModuleSyntax`.
`LayerId` — брендированная строка: произвольную строку вместо идентификатора не передать.

## 7. Рассмотрено и отклонено

| Вариант                                                                              | Почему нет                                                                                                                                           | Когда передумаю                                           |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Ключ верхнего уровня на слой** (`on("layer:42")`) — выглядит как точечная подписка | верхний уровень копируется при каждом диспатче: копия 100 ключей дороже, чем 100 дешёвых колбэков. Плюс новые ключи верхнего уровня добавлять нельзя | — выигрыш в уведомлениях съедается копированием           |
| **Кэш данных между включениями**                                                     | скрыл бы статус `loading` при повторном включении — поведение хуже читается                                                                          | реальная стоимость запросов                               |
| **`useCallback` на хендлерах строки**                                                | строка перерисовывается только при изменении своих данных, её дети — в любом случае. Мемоизация ничего бы не изменила                                | если строка станет тяжёлой и появятся `memo`-дети         |
| **Epoch-счётчик для гонок**                                                          | второе представление того же факта, которое надо синхронизировать                                                                                    | если поколение понадобится там, где `AbortController` нет |

## 8. AI-инструменты

Основной инструмент — **Claude Code** (Anthropic). Использовался в трёх ролях.

**Исследование, а не генерация.** Пакет был скачан из npm-реестра и прочитан
построчно вместе с моделью — отсюда особенности из раздела 3. Каждая перепроверена
по исходнику, а не принята на слово.

**Проектирование.** До кода: разбор вариантов формы состояния с компромиссами,
журнал решений с условием пересмотра для каждого, план по коммитам с точкой
проверки у каждого шага. Спека прошла независимое ревью, которое нашло
несколько реальных нестыковок — например, что строка «ответ отброшен» в демо
не появилась бы никогда, потому что честный mock всегда успевает отменить запрос.

**Реализация в паре.** Код писался вместе с Claude Code: я ставил задачу и принимал
решения, модель предлагала план и реализацию, каждое изменение проверялось перед
коммитом. Приёмы, которые оказались полезнее всего:

- **мутационная проверка тестов** — защита намеренно ломается, тест обязан упасть;
  так проверены все тесты на гонки, отмену, утечки и рендеры;
- **эксперимент вместо предположения** — например, что счётчик на `useRef` под
  StrictMode показывает 2 вместо 1, а `Profiler` — честную 1, выяснено тестом до того,
  как выбирать реализацию;
- **проверка в реальном сборщике** — интероп CommonJS-пакетов проверялся сборкой через
  Rolldown, после того как белый экран показал, что Node и Vitest ведут себя иначе, чем Vite.

AI не заменял понимание: всё, что есть в коде, я могу объяснить и защитить.
Правила проекта для AI-ассистента лежат в [`CLAUDE.md`](./CLAUDE.md).
